# خطة تنفيذ فصل أدوار إتقان — لا تطبيق إنتاجي قبل التحقق

**القرار المعتمد:** مدير الموقع ودور مدير المدرسة منفصلان، ويمكن للحساب الواحد جمعهما إذا حصل على عضوية مدير مدرسة نشطة في مدرسة محددة. القرار موثق في `docs/ITQAN_GOVERNANCE.md`.

## خط أساس الإنتاج — قراءة فقط (11 نوفمبر 2026)

| فحص | نتيجة القراءة |
|---|---:|
| حسابات `site_admin` | 1 |
| منها بحساب مدير مدرسة نشط في أي مدرسة | 0 |
| منها بعضوية مدرسية نشطة من أي نوع | 0 |
| أذونات `school.*` الموروثة من `site_admin` | 9 |
| أذونات `system.*` المركزية | 4 |

**أثر مهم:** مدير الموقع الحالي ليس مديرًا لأي مدرسة وفق سجل عضوياته. عند تطبيق الفصل لن يستطيع فتح لوحة المدرسة أو إجراء عمليات مدير المدرسة؛ لكنه سيحتفظ بوصوله المركزي للمدارس والمستخدمين والمعايير. لا ينبغي منحه عضوية مدرسة تلقائيًا؛ إضافة دور مدير مدرسة تتطلب قرارًا إداريًا محددًا للمدرسة.

## قائمة العمل المنفذ برمجيًا

1. إضافة ترحيل مستقل `20261111141500_separate_site_and_school_roles.sql`: حذف التسعة أذونات `school.*` من دور `site_admin` وإزالة تجاوز `has_system_permission` من `itqan_private.has_school_permission`. يحتفظ بالدوال والأذونات المركزية والعضويات والبيانات دون حذف.
2. تغيير حماية Worker بحيث لا يفتح مدير الموقع لوحة المدرسة دون عضوية نشطة، ولا يرى قائمة أعضاء مدرسة عبر مسار مديري المدارس دون عضوية مدير مدرسة في تلك المدرسة.
3. تحديث لوحة المدرسة لعرض الدور المدرسي الحقيقي، وتصفية المدارس بحسب عضوية الحساب، بدل إظهار مدير الموقع تلقائيًا كمدير مدرسة.
4. توثيق سياسة الفصل في `AGENTS.md` و`docs/ITQAN_ROADMAP.md` و`docs/ITQAN_GOVERNANCE.md`.
5. اختبار سلبي وإيجابي على أساس Role-Based Access Control وSchool-Based Access Control، مع ضمان استمرار سياسة مشاركة الشواهد الذاتية `personal_evidence_shares` التي تستخدم `self.manage_portfolio` بشرط عضوية مدرسة نشطة:
   - مدير موقع فقط يدير النظام ولا يدير مدرسة.
   - مدير مدرسة فقط يدير مدرسته ولا يملك التحكم المركزي.
   - موظف يرى خدماته فقط.
   - حساب يحمل الدورين ينفذ كلا الدورين مع **تقييد مدرسة المدير**.
   - رفض الوصول العابر لمدرسة أخرى.
   - سحب العضوية أو تعطيل المدرسة أو تعطيل المستخدم يلغي سلطة المدرسة فورًا ولا يتطلب انتهاء صلاحية JWT.
6. اختبارات JavaScript للواجهات والبوابات؛ اختبارات SQL لـRLS/RPCs والمراحل السابقة في Supabase معزولة.

## بوابات التطبيق والإطلاق

- [ ] نجاح `npm test` و`npm run check` على أحدث التزام في CI.
- [ ] نجاح `schema-bootstrap` على جميع ملفات الترحيل واختبارات الأذونات المركزية والمدرسية والتقييم والشواهد والنقل.
- [ ] فحص تعارضات الترحيلات الثلاثة السابقة (`20261111133000` و`20261111134500` و`20261111135500`) مع سجل الإنتاج (آخر مؤكد 41 ترحيلًا).
- [ ] التحقق من أن مدير الموقع يستمر في إدارة المدارس والمستخدمين والمعايير من لوحة الموقع.
- [ ] عرض أثر سحب صلاحيات مدير المدرسة عن حساب مدير الموقع الحالي (لا توجد له عضوية) لاعتماد الاستمرار بهذه السياسة.
- [ ] نسخة احتياطية مناسبة لجدول `role_permissions` وتعريف `itqan_private.has_school_permission` وسجل الترحيلات قبل التطبيق.
- [ ] تفويض مستقل **لتطبيق** الترحيلات على Supabase الإنتاجي، وليس مجرد الموافقة على تصميمها.
- [ ] توثيق خطة تراجع باستعادة الأذونات التسعة المستندة إلى اللقطة السابقة، وإصدار ترحيل تصحيحي جديد عند الحاجة؛ لا تعديل لسجل الترحيلات التاريخية.
- [ ] اختبارات القبول التشغيلية والبصرية (كمبيوتر أولًا ثم جوال) تبقى مؤجلة حتى اكتمال كل المهام البرمجية.

## ضوابط المخاطر

- **لا توريث:** تسجيل `site_admin` لا يمنح `school.*`، ولو كان للحساب `user_roles` مركزي.
- **لا إضافة تلقائية:** لا يتم إدراج عضويات مدرسية للإداريين أثناء الترحيل.
- **الإدارة المركزية ليست دور مدير مدرسة:** تبقى سياسة `schools_read_authorized` وعمليات إدارة المدارس والمستخدمين المركزية، ولا تتحول إلى صلاحيات تقييم.
- **الحدود المتعددة:** إذا أمكن تعيين العضوية المدرسية نفسها لمدرستين مستقبلاً، فكل عملية تتطلب `school_id` مطابقًا لعضوية صالحة وفق ضوابط عضوية الموظف النشط.
- **حارس واجهة + قاعدة البيانات:** لا تكفي إخفاء قائمة أو عرض خيار لتأمين endpoint؛ يجب تحقق Worker والدوال المحمية.
- **لا إنتاج:** مجرد دمج الترحيل في `main` ليس تفويضًا لتطبيقه على Supabase أو Cloudflare، ولا دليلًا على قبول الواجهات بصريًا.
