**التاريخ:** 2026-11-12  
**الحالة:** معتمدة للدراسة والتخطيط فقط؛ غير معتمدة للتنفيذ  
**المستودع المضيف:** `alharbikh/itqan`  
**المستودع المصدر:** `alharbikh/student-services`  
**نطاق القرار:** توثيق الدراسة وخطة المهام في GitHub، **دون أي تعديل برمجي أو ترحيل أو نشر أو حذف بيانات**.

## 1. ملخص القرار

يُقترح استيعاب خدمات الطلاب كوحدة وظيفية مستقلة داخل منصة إتقان (Modular Monolith) مع إعادة استخدام التأسيس المركزي: الهوية، المدارس، المستخدمون، عضويات المدارس، السنوات والتقويم، الأذونات، إتاحة الخدمات والتدقيق. لا يتم خلط بيانات الطلاب وبيانات الموظفين أو منح صلاحيات إحداهما تلقائياً للأخرى. **لم يعتمد المالك بعد بدء تنفيذ الدمج**؛ إنشاء هذه الوثيقة والقضايا أعمال إدارية فقط.

## 3. مقارنة التأسيس وحسم الاتجاه المبدئي

| العنصر | إتقان | خدمات الطلاب | الاتجاه المستهدف (غير منفذ) |
|---|---|---|---|
| المصادقة | Supabase Auth | وثيقة التأسيس: Cloudflare Access؛ شيفرة قديمة: جلسات signed-cookie | حسابات Supabase المركزية؛ لا تُنقل جلسات النظام القديم |
| المدارس | `public.schools` | مدارس مقترحة في المخطط | مرجع مدرسة موحد، دون تكرار |
| المستخدمون | `public.users` و `user_roles` | مستخدمون وهوية Access مخططة | مستخدمون مركزيون؛ لا إنشاء حساب مكرر |
| عضويات المدارس | `school_memberships` | عضويات مدرسية مخططة | عضوية أمنية واحدة مشتركة مع أذونات خدمة مستقلة |
| الموظفون | `employees`, `school_employees` | ليسوا السجل المركزي للطلاب | عدم الخلط بين العضوية الأمنية والتوظيف التاريخي |
| السنوات الدراسية | `academic_years` | سنة واحدة منشورة/نشطة مع حالات وتواريخ مدرسية | تحليل توافق مخطط إتقان وتاريخ تقييماته قبل أي تعديل |
| التقويم | لا يُفترض توافر نفس عقود الاستثناءات | تقويم مركزي واستثناءات المدرسة مخططان | تأسيس تقويم مشترك بعد جرد تنفيذي |
| تفعيل الخدمات | `platform_services`, `school_service_access` | `services`, `school_services` مخططان | إعادة استخدام إتقان مع صلاحيات منفصلة |
| قاعدة البيانات | Supabase PostgreSQL + RLS/RPC | D1/SQLite، قديم مقابل مستهدف | دراسة نقل جداول الطلاب إلى PostgreSQL بمخطط مستقل |
| الواجهات والنشر | Workers + أصول عامة | Workers + TypeScript/Vite | وحدات مستقلة ضمن تطبيق واحد، دون دمج مباشر للبناء أو إعادة هيكلة فورية |

## 4. الحدود الأمنية والتعاقدات

1. مدير الموقع `site_admin` لا يرث `school.*`؛ مدير المدرسة لا يرث `system.*`، ويمكن للحساب حمل الدورين فقط بعضوية مستقلة معتمدة.
2. أي API أو RPC أو جدول لبيانات الطلاب يتحقق من `school_id` والعضوية النشطة وإتاحة الخدمة والإذن المحدد؛ منع العبور بين المدارس والربط بالاسم وحده.
3. تُعزل جداول الطالب ومصادر الغياب والاتصال والتقارير عن بيانات تقييم الموظفين. دراسة مخطط PostgreSQL مستقل `student_services` مع RLS افتراضيًا، وليس نقل D1 SQL حرفياً.
4. الطالب وولي الأمر والهوية المصدرية ليسوا حساب مستخدم موظف؛ ربط السجلات الرسمية لاحق ويخضع للتحقق.
5. لا تُنسخ بيانات طلاب حساسة إلى GitHub، ولا تُحذف أو تُهاجر بيانات الإنتاج أو D1 في هذه الموافقة.
6. لا تُعد حالة السنة المنشورة أو صلاحيات المدير معتمدة تقنيًا قبل اختبار أثرها على ملفات وتقييمات إتقان التاريخية.

## 5. نطاق الدراسة فقط / خارج النطاق

**داخل النطاق الحالي:** الوثائق، خطة المهام، الاعتماديات، معايير القبول المستقبلية، فهرس تعارضات، وروابط المصدر.  
**خارج النطاق:** ملفات التطبيق، نقل المجلدات، تحديث الواجهات، إنشاء SQL migrations، تغيير Auth/Access/DNS/Cloudflare، تشغيل ترحيلات Supabase أو D1، نقل/حذف بيانات، النشر، أرشفة المستودع الأصلي، تشغيل اختبارات القبول الفعلية.

## 7. بوابات القرار

- **G0 (متحقق):** موافقة المالك على *التوثيق وإنشاء القضايا فقط*.
- **G1 (معلق):** موافقة مستقلة على بدء تغيير الشيفرة.
- **G2 (معلق):** موافقة مستقلة على إنشاء/تطبيق الترحيلات، بعد مراجعة سجل إنتاج Supabase وتعقيدات الترقية.
- **G3 (معلق):** موافقة مستقلة على ترحيل أي بيانات فعلية، مع نسخة احتياطية والتراجع.

## 8. نتيجة الدراسة

**التوصية المعمارية، وليست تصريح تنفيذ:** استضافة خدمات الطلاب داخل إتقان كوحدة مستقلة، وتوحيد التأسيس والأمان على Supabase، مع إبقاء مستودع `student-services` وبيئته الحالية بلا تغيير إلى أن تُعتمد خطة انتقال متحققة. لا يُسمح باستنتاج أن التوحيد بسيط أو أن المخططات الجديدة مطبقة بالفعل.
