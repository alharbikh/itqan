## نتائج مراجعة Supabase الحقيقية — معلومات تدقيق وليست قبول أمان

قراءة حية بتاريخ 11 نوفمبر 2026، دون تعديل قاعدة الإنتاج:
- المشروع فعال `ACTIVE_HEALTHY`.
- منح `TRUNCATE` للدور `authenticated` على **21 جدولًا**، وكذلك `TRIGGER`/`REFERENCES` على 22 جدولًا؛ يجب إزالة الزائد بعد اختبار التبعيات. `TRUNCATE` لا يخضع لـRLS، لكن PostgREST لا يتيح أمر TRUNCATE كعملية REST عادية.
- 43 دالة `SECURITY DEFINER` يمكن للدور `authenticated` استدعاؤها. **فحص أولي فقط** للنصوص عبر `pg_get_functiondef` أظهر أن جميع الـ43 تشير إلى `auth.uid()`؛ ليس ذلك إثباتًا كافيًا لصحة التفويض الداخلي بجميع المسارات.
- 10 جداول RLS بلا سياسة صفوف (INFO)؛ قد تكون جداول وصولها محصورًا بدوال RPC.
- تحذير Auth لتفعيل حماية كلمات المرور المسرّبة، يتطلب مراجعة سياسة المصادقة.
- 43 مفتاحًا خارجيًا بلا فهرس و3 تكرارات سياسات `permissive`. قراءة السياسات المتكررة بينت أن بعضها يفصل قراءة المالك عن المشاركة أو المدراء؛ لا تُحذف سياسات قبل اختبار العزل.
- تم فتح [#24](https://github.com/alharbikh/itqan/issues/24) لتقليل امتيازات القاعدة ومراجعة الدوال مع اختبار معزول؛ **لم يُطبّق ترحيل إنتاجي جديد**.

## بوابات الإغلاق
1. نجاح `npm test` و`npm run check`، وإعادة بناء Supabase معزولة على رأس أي PR قبل الدمج.
2. الفصل بين إثبات وجود واجهة/خادم واختبار تعامل مستخدم حقيقي.
3. لا يُعتمد الإغلاق البرمجي الشامل قبل إتمام #24 أو توثيق قرار إداري بقبول الخطر مؤقتًا، ومطابقة عناصر GitHub Projects التي لم تكن قابلة للقراءة.
4. الامتناع عن إنشاء بيانات تجريبية في الإنتاج وتجنب أي تغيير DNS.
