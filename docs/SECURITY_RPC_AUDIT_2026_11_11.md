# تدقيق دوال Supabase المحمية والعزل — إتقان سمارت برو

**النطاق:** مراجعة أمان تقنية لدوال `public SECURITY DEFINER`، ومنع الحسابات المعطلة، وجداول `public` غير المعروضة عبر Data API، بتاريخ 11 نوفمبر 2026. لم يُنفّذ اختبار بصري أو عملية RPC بإجراء مستخدم حقيقي في الإنتاج.

## نتائج المراجعة المباشرة للإنتاج

| بند الفحص | النتيجة | الدلالة |
|---|---:|---|
| الدوال `SECURITY DEFINER` المستدعاة بدور `authenticated` | 43 | سطح الوصول للـRPC العام |
| الدوال نفسها المستدعاة بدور `anon` | 0 | لا منح EXECUTE مجهول مباشر |
| دوال `authenticated` ذات مرجع `auth.uid()` | 43/43 | فحص هوية بنيوي؛ ليس برهان تفويض منفردًا |
| دوال `authenticated` ذات `search_path` صريح | 43/43 | تقليل مخاطر تغيير سياق أسماء SQL |
| الدوال ذات إشارة لمساعد أذونات مدرسة/نظام | 31 | المساعدان `itqan_private.has_school_permission` و`has_system_permission` يشترطان `users.status='active'` |
| دوال لا تتحقق من حالة الحساب مباشرة ولا تستخدم مساعد الصلاحيات | **9** قبل الترحيل الجديد | فجوة التعامل مع JWT لا يزال صالحًا بعد تعطيل الحساب |
| جداول RLS بلا سياسات صفوف | 10 | كلها RLS مفعّل ولا تملك أدوار `anon` أو `authenticated` صلاحيات DML مباشرة |
| منح `TRUNCATE/TRIGGER/REFERENCES` الزائدة | 0 | أزيلت من الإنتاج في الترحيل `20261111112500` بعد نجاح الاختبارات |

## فجوة الحساب المعطّل — المعالجة

قد يبقى رمز وصول Supabase JWT صالحًا لبعض الوقت بعد تغيير `public.users.status` إلى `disabled`. لا تكفي حماية واجهة Cloudflare وحدها إذا أمكن استدعاء RPC عبر Supabase Data API مباشرة.

الترحيل المقترح `20261111114500_reject_disabled_account_privileged_rpcs.sql` يضيف رفضًا مبكرًا للمستخدم غير النشط، دون تغيير واجهة الدالة أو شرط ملكية السجل والتفويض الأصلي، إلى:

1. `itqan_employee_ack_midyear` — إقرار الموظف بالمراجعة.
2. `itqan_personnel_my_profiles` — استعراض ملفات الموظف.
3. `itqan_personnel_my_requests` — استعراض طلباته.
4. `itqan_school_score_criterion` — إدخال درجة معيار.
5. `itqan_school_submit_review` — تقديم التقييم.
6. `itqan_school_exception_criteria` — معاينة معايير استكمال التقييم.
7. `itqan_school_exception_score` — تعديل درجة الاستثناء.
8. `itqan_school_exception_submit` — إرسال استكمال التقييم.
9. `itqan_school_request_review_exception` — طلب استكمال مراجعة مجمدة.

هذه الدوال تشترط أصلًا `auth.uid()` وملكية السجل أو حالة الدورة، لكنها كانت لا تفحص `users.status='active'` في جميع الحالات. الترحيل يُجرّب أولًا عبر `supabase db reset --no-seed` في قاعدة مؤقتة.

## اختبارات منع التراجع

- `supabase/tests/disabled_account_rpc_guard.sql`: مستخدم معطّل واختبار رفض الدوال التسع بإشارة `42501`؛ المستخدم النشط يستمر في قراءة قوائمه؛ كل بيانات الاختبار ضمن `BEGIN ... ROLLBACK`.
- `supabase/tests/security_definer_contract.sql`: حسابات `anon` لا تستدعي دوال محمية؛ الدوال المعروضة تتضمن مرجع الهوية وإعداد `search_path`؛ جميعها تفحص حالة المستخدم مباشرة أو تعتمد على مساعد صلاحيات يفحصها.
- `supabase/tests/closed_tables_exposure.sql`: تأكيد أن أي جدول RLS بدون سياسة لا يمنح متصفحًا `SELECT/INSERT/UPDATE/DELETE/TRUNCATE/TRIGGER/REFERENCES`.
- اختبارات الأداء/الربط/النقل/المرفقات/أدوار الإدارة الحالية تُنفّذ بعد هذه الترحيلات على القاعدة المؤقتة.

## التحذيرات التي لا يعالجها الترحيل

- تحذير `authenticated_security_definer_function_executable` قد يستمر في Supabase Advisor لأن RPCs مقصودة لدور `authenticated` وتستخدم صلاحيات منشئها. اختبارات الصلاحيات الحالية تقلل الخطر، ولا يعني العدد 43 وحده ثغرة، ولا يجوز تعطيل EXECUTE تلقائيًا عن جميعها.
- `auth_leaked_password_protection`: يحتاج تغيير إعداد Supabase Auth، وليس ترحيل PostgreSQL. يجب التحقق من سياسات المصادقة وأثر تفعيل الخيار، ولا يمكن إثبات تفعيله من CI لقاعدة بيانات مؤقتة.
- الاختبارات أعلاه لا تحل محل اختبارات حسابين حقيقيين من مدرستين مختلفتين أو اعتماد القبول البصري، وكلاهما مؤجلان حسب توجيه المالك.
