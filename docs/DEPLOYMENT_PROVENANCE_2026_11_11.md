**أسلوب المطابقة:** قرأنا `GET /accounts/{account_id}/workers/scripts/itqan/content/v2` بدون تغيير أي مورد؛ الملف Multipart يحتوي `worker.js.map` مع `sourcesContent[0]` لمصدر `src/worker.js`. حُسبت بصمة Git blob SHA-1 بترميز Git الصحيح `blob <UTF8 byte count>\0<UTF8 source>` وقورنت مع SHA المعاد من GitHub API للملف في `main`. **النتيجة تطابق كامل لبصمة الملف المصدر**، وليس مجرد تشابه نصوص أو اسم نسخة.

**الحدود:** لا يمكن الجزم بتطابق *كل الملفات الثابتة المنشورة* من Source Map الخاصة بـWorker؛ كما أن تطابق المصدر وحده لا يثبت تاريخ الالتزام الكامل أو النشر من محطة عمل معينة. لا يحمل إصدار Cloudflare المعروض وسم Git commit SHA. نُفذت مراجعة منفصلة لنشر Worker وسجلات Supabase، لكن القبول المرئي بحساب مستخدم حقيقي مؤجل.

## مصدر النشر

- Cloudflare سجلت `source=wrangler` وبيانات مؤلف الرفع في إصدار Worker ومعلومات النشر؛ هذه أقوى قرينة متاحة على قناة الرفع وليس على من ضغط زرًا فعليًا أو على الجهاز المصدر.
- `Workers Builds triggers`: لا يوجد أي مشغّل مفعّل في النتائج المقروءة.
- `Workers deploy hooks`: لا يوجد أي Deploy Hook في النتائج المقروءة.
- في GitHub يوجد workflow تحقق `.github/workflows/verify.yml`، ولم نجد ملف `.github/workflows/deploy.yml` أو سير عمل نشر مثبتًا في مراجعة الإعدادات.
- لذلك لا يوجد دليل على نشر تلقائي عبر Workers Builds أو Deploy Hooks المعرّفة؛ **ولا يصح نفي احتمال نشر Wrangler خارجي يدوي أو من أتمتة أخرى لا تعرضها هذه القوائم**.
- أي إصدار مستقبلي يجب أن يسجل Git SHA والنسخة المنشورة، ويمر عبر تدقيق صلاحيات النشر، مع فصل صلاحيات دفع الإنتاج عن التحقق الآلي.

## أدوات التحقق القابلة لإعادة التشغيل

### المصدر الأصلي المنشور

`node scripts/verify-deployed-worker.mjs --bundle <exported-content-v2.multipart>`

أو تعيين `CLOUDFLARE_API_TOKEN` و`CLOUDFLARE_ACCOUNT_ID` مؤقتًا في بيئة التنفيذ ثم:

`node scripts/verify-deployed-worker.mjs`

- لا تضع رمز Cloudflare في المستودع أو سجل GitHub Actions.
- يتوقف بفشل واضح إذا لم يحتوي تصدير Cloudflare على `src/worker.js` أو اختلفت بصمته عن نسخة المستودع الحالية.
- عند تغيّر `main` قبل نشر Worker جديد، قد تكون النتيجة عدم تطابق متوقع: يُسجل كفرق نشر، لا سببًا لإعادة نشر إنتاجية دون تفويض.

### الملفات الثابتة العامة

`node scripts/verify-public-assets.mjs`

يفحص JS/CSS عامة عبر طلبات HTTPS GET فقط، دون أي جلسة أو بيانات مستخدم، ويقارن SHA-256 للبايتات المعادة بالملفات في `public/`. توجد أيضًا مهمة GitHub Actions `production-audit.yml` يمكن تشغيلها يدويًا، وتُشغّل مرة عند إضافة أو تحديث كود أداة التحقق على `main`.

**نجاح اختبارات ملفات الواجهة الحية لا يعني النجاح البصري أو نجاح تسجيل الدخول الفعلي.** إذا فشل اختبار ملف، ادرس اختلاف النسخة أو التخزين المؤقت أولًا بدل نشر تلقائي.

## إثبات اتساق الأدوار مع Supabase

- Supabase الإنتاجية بعد صيانة #39: **45 ترحيلًا**، وصفر صلاحيات `school.*` موروثة لـ`site_admin`، مع الحفاظ على `system.*` وصلاحيات مديري المدارس.
- Worker الأصلي المطابق لـGitHub يحتوي حارس عضوية مدير المدرسة الذي يمنع توريث صلاحيات مدير الموقع.
- اختبارات قاعدة البيانات المستقلة بعد التطبيق أكدت صلاحيات مدير الموقع ومدير المدرسة والموظف وعدم عبور المدرسة.
- تبقى **اختبارات القبول التشغيلي والبصري على الكمبيوتر والجوال مؤجلة** وفق قرار المالك، ولا يجوز إغلاقها على أساس هذه الاختبارات التقنية فقط.
