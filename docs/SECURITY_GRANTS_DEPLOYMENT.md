# خطة اعتماد ترحيل تقليص امتيازات Supabase — ITQAN #24

**الحالة:** الترحيل جاهز برمجيًا للاختبار المعزول؛ **لا يُنفذ على الإنتاج دون إذن صريح منفصل**.

## الخلفية

فحص الإنتاج بتاريخ 11 نوفمبر 2026 أظهر امتيازات على جداول `public` لدور `authenticated`: `TRUNCATE` على 21 جدولًا، و`TRIGGER` و`REFERENCES` على 22 جدولًا لكل منهما. `TRUNCATE` لا تخضع لعزل صفوف RLS. أما `anon` فلم يظهر له منح مباشر لهذه الامتيازات.

الترحيل المستقل:

`supabase/migrations/20261111112500_revoke_public_table_unsafe_browser_grants.sql`

يلغي فقط ثلاث فئات امتيازات عن الدورين `anon` و`authenticated` على جداول `public`. لا يغيّر الصلاحيات الاعتيادية `SELECT/INSERT/UPDATE/DELETE`، ولا `EXECUTE` للدوال المحمية، ولا الجداول أو بياناتها. يتضمن فحصًا لاحقًا يجهض المعاملة إذا بقيت الصلاحيات.

## أدلة الاختبار

- GitHub Actions `schema-bootstrap` تعيد تكوين قاعدة بيانات مؤقتة عبر الترحيلات كاملة، **بما فيها الملف الجديد**.
- `supabase/tests/no_excess_table_grants.sql` تفحص غياب `TRUNCATE`/`TRIGGER`/`REFERENCES` بعد إعادة البناء.
- جميع اختبارات الإدارة/الأدوار/العضويات/الربط/النقل/إطارات المعايير/الأداء/المرفقات تتبع هذا الفحص، لكشف أي تراجع وظيفي.
- `app-and-security` تغطي خادم Cloudflare وواجهاته.
- لا يُدمج هذا الطلب حتى تنجح الوظيفتان على آخر التزام.

## ضوابط التطبيق على الإنتاج (مرحلة مستقلة)

1. وجود تفويض خاص بالتطبيق الإنتاجي، وتأمين نسخة احتياطية مناسبة لقاعدة Supabase، والتحقق من بقاء #26 مغلقة وسجل الترحيلات مطابقًا لملفات GitHub.
2. تسجيل لقطة الصلاحيات الحالية **دون أسماء مستخدمين أو بيانات شخصية**:
   ```sql
   select table_name,grantee,privilege_type
   from information_schema.role_table_grants
   where table_schema='public'
     and grantee in ('anon','authenticated')
   order by table_name,grantee,privilege_type;
   ```
3. مطابقة عدد الجداول وإصدارات الترحيلات الحالية مع المعتمد، والتحقق من عدم وجود ترحيلات أخرى معلقة. عدم استخدام `supabase db reset --remote` أو إعادة تشغيل SQL تاريخي.
4. تطبيق **الترحيل الجديد فقط** وفق المسار الرسمي لتطبيق الترحيلات بعد مراجعة قائمة الملفات المعلقة. لا تكرار ترحيلات سابقة.
5. إعادة قراءة الامتيازات بعد التنفيذ؛ `TRUNCATE/TRIGGER/REFERENCES` يجب أن تساوي صفرًا في جميع جداول `public` للدورين، مع بقاء الامتيازات الأخرى كما كانت.
6. التحقق من عدم تراجع تسجيل الدخول والطلبات الإدارية والعلاقات المدرسية والملفات والشواهد؛ تُجرى اختبارات التشغيل الفعلية في مرحلة قبول منفصلة حسب قرار المالك.
7. توثيق التوقيت ونسخة Git SHA وحالة الترحيل في GitHub، دون معلومات اعتماد أو محتوى شخصي.

## آلية التراجع عند الحاجة

لا تستخدم `GRANT ALL` أو تعدّل ملفات ترحيل تاريخية. عند اكتشاف عطل فعلي:
- توقف عن أي تطبيقات ترحيل إضافية.
- قارن لقطة الامتيازات قبل وبعد الإجراء على الجدول والفئة المحددين.
- إن كان العطل راجعًا إلى امتياز ألغي خطأً، أعد **فقط الامتياز السابق المثبت بالدليل** على الجدول المتأثر، بعد مراجعة أمنية وإدارية، مع توثيق الاستثناء وتحديد صلاحية مؤقتة.
- أنشئ ترحيلًا تصحيحيًا جديدًا بعد اختبار الحالة في بيئة معزولة؛ لا تعبث بتاريخ `supabase_migrations`.
- احتفظ بنسخة تاريخ الترحيلات `supabase_migrations.itqan_history_backup_20261111_pre_repair` التي أُنشئت أثناء #26 ولا تخلطها بنسخة كاملة من بيانات التطبيق.

## أعمال أمنية مستقلة ما زالت مفتوحة

تحذير Supabase بشأن 43 دالة `SECURITY DEFINER` مسموحة لـ`authenticated` ليس محصورًا بامتيازات الجداول. كل دالة تحتاج مراجعة منطق `auth.uid()` وقيود الدور/المدرسة ومنع كشف بيانات مدارس أخرى؛ وجود `auth.uid()` بالنص وحده ليس دليل أمان. حماية كلمات المرور المسرّبة من إعدادات Auth، وليست جزءًا من هذا الترحيل. لا يُغلق #24 بالكامل بمجرد دمج SQL إلا بعد توثيق معالجة بقية التحذيرات أو فصلها إلى مهام صريحة.
